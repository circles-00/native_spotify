# Android native local playback replacement

**Decision (November 20, 2026): No cutover.** Native Media3/ExoPlayer is the proposed Android renderer, but it is not a Spotify stream provider. No documented or separately authorized source was found that supplies full Spotify tracks and, where required, playback licenses for this app's ExoPlayer instance. Keep Android's existing setup and routing, desktop Soloist, and remote Web API controls intact.

## Evidence and authorization

- The latest Soloist attempt on the Galaxy started the process but never established a Connect session. Outify skipped tracks with `error audio key 0 1` even with Soloist and Termux stopped. These are separate failure observations, not a diagnosis of either backend.
- The user heard Spotify audio in the separate Stopify Native Test APK. The local test checkout at `/tmp/opencode/stopify-native-test` is a modified tree based on [Stopify 1.0.0](https://github.com/Anattana-Labs/Stopify/tree/1.0.0), commit `38da838`. The upstream code license is MIT (copyright 2026 Shashwat; retain its copyright and permission notice if reusing covered code). The test modifications are not the tagged release. The upstream README describes reverse-engineered private Web Player playback and a WebView that obtains Web Player credentials; the native player uses Media3. The MIT grant covers code, not Spotify's service, credentials, DRM, or content. Audible audio does not establish process-death recovery, authorization, or support. Do not port its private playback path or reuse probe credentials.
- Spotify's [Web API play endpoint](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback) commands an existing device and returns no stream or license. The [Android SDK](https://developer.spotify.com/documentation/android) delegates rendering to the Spotify app. The [Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk) renders in a browser, outside the project's auth-only WebView exception. The [commercial hardware eSDK](https://developer.spotify.com/documentation/commercial-hardware) is partner-only and not an available Media3 source for this app.
- Review the [Spotify Developer Terms, §§ III–IV](https://developer.spotify.com/terms) and [Developer Policy, §§ III–IV](https://developer.spotify.com/policy) before proceeding. They restrict unauthorized access and credential collection, require Premium for music streaming via the platform, and require prior written permission to replace a core Spotify experience. The unblocker is a provider-supported contract or written authorization for this use case **and** an entitled full-track media/DRM handoff compatible with Media3. A first-party auth server, Premium login, preview clips, and fixture audio do not supply that handoff.

## Proposed integration after authorization

| Layer | Change |
| --- | --- |
| `src/core/engine.h`, `src/core/app_workers.c` | Extend the existing engine boundary with typed local commands and capabilities. Branch in `app_run_player` before Spotify player calls for a selected native-local route. Keep existing Soloist dispatch and remote `spotify_*` dispatch unchanged. |
| `src/platform/android_system.c`, `android_host.h`, `android/app/src/main/cpp/bridge.c`, `CoreHost.kt` | Post validated commands onto the player's looper through the existing host; return events through JNI to the core's locked state/event path and wake snapshot consumers. Update JNI keep rules for release builds. |
| `PlaybackService.kt` | Own a single ExoPlayer, Android media session, and supervised scope. Send media-session and notification actions through the same `Core` actions as Compose; the existing sleep timer's `ACTION_PAUSE` also uses this route. Do not expose direct media-session transport commands that bypass the core's queue. |
| `Engine.kt` and setup | After verification, replace install/key/pair with local playback sign-in and local readiness/error states. These must not change Web API login or browsing readiness. |

### Command and event contract

- Open a single item with a content URI, request ID, and optional initial position in milliseconds. Also support resume, pause, seek, and stop. Scope transport commands to the active route generation and, for track-specific operations, the active request. Validate arguments, copy strings before enqueueing, and dispatch outside the core lock. A successful return means **accepted for dispatch**, not started; rejection must clear pending state for the current request without falling through to another device.
- Keep desired request and loaded item identity separate. Invalidate the old request before replacing it. Cancel superseded resolution, and recheck request identity and desired playback state on the looper before setting the item or starting audio. Pause and sleep expiry must not allow a pending resolution to start audio later; route changes and shutdown invalidate pending work. Seek only the identified loaded item, clamp to the known seekable range, and never resolve a token for a seek.
- Tag media items with the request ID. Report transition, buffering, confirmed play/pause, position discontinuity (with seek sequence for seek reconciliation), end, and typed errors. Carry the service generation, originating request ID, URI where relevant, position/duration in milliseconds, and capability flags. Do not relabel an old callback with the newest ID. Validate generation, active route, and request ID under the core lock before changing state; discard late callbacks even for repeated taps on the same URI. Use position samples at state changes and while needed for progress or lyrics, not an idle polling loop.
- C chooses Next/Previous, repeat, shuffle, restored position, and queue advancement. A confirmed `ENDED` advances at most once; auth failure is not end-of-track and never drains the queue. Represent the native player as an in-app local target, not a fabricated Spotify Connect device ID. While it is selected, remote polling must not overwrite its playback or up-next snapshot. Selecting a remote device explicitly invalidates and stops local playback and uses the existing remote command path. Do not silently start remote playback on local failure.

### Service and playback session

- The service owns player creation, audio focus/noisy-output handling, and media foreground lifecycle. Activity recreation only reattaches UI; it does not recreate the player. On shutdown invalidate request generation, cancel work, detach listeners, release the player and media session on the application looper, and remove the foreground notification. Do not auto-start audio after process death.
- Keep `PlaybackSession` (sign-in, refresh, secure storage) and `AuthorizedPlaybackSource` (provider exchange and entitlement-aware resolution to a `MediaItem`) separate in Kotlin. Use a distinct account namespace with the existing Keystore-backed `Secrets.kt` if it satisfies the durability contract; verify write success and fail closed on unavailable keys or failed storage. No plaintext fallback. No playback credentials, authorized media URLs, or license headers across JNI or in logs. Keep the session bearer scoped to its provider endpoint, not a CDN or redirect.
- `AGENTS.md` allows an Android WebView only for sign-in and on-demand refresh. Prefer the authorized provider's supported auth flow. If it supports the WebView model, use a visible first sign-in and an ephemeral WebView in the same app profile for refresh. Validate exact HTTPS callback origin/path, state, and PKCE. Require a persistent Secure, HttpOnly session cookie if relying on cookie reuse; flushing does not make a session-only cookie persistent. Apply a bounded timeout and destroy the WebView on success, failure, timeout, or cancellation. On playback sign-out, invalidate in-flight work, revoke/clear playback credentials and applicable cookies, and leave the Web API session alone. No WebView is added while the source is blocked.
- Refresh only when demanded by play. Share a refresh in the supervised session scope so canceling play A does not cancel the refresh awaited by play B. Serialize interactive sign-in against silent refresh and gate new local play while signing in. Recheck token identity before invalidation; on token rejection allow one forced refresh and one resolution retry for the current request. Revocation prompts sign-in; entitlement, unsupported content, and network failures are separate errors and must not trigger refresh loops or queue-wide retries.
